## 1. 最终结论

C3-Mass 已经不是“只有 C3 曲线的原型”。当前代码已经具备：

- Flask + SQLite + YAML 备份的火箭资料库；
- 发动机 CFG 解析、级段与多发动机组计算；
- C3 / 剩余 Δv 曲线、标准任务与任意地球轨道查询；
- 逐级、多次点火的任务求解、容量搜索、可行性判断与前端时间线；
- `.craft` / `.loadmeta` 预览、SSTU 布局识别、KSP 安装索引、部件匹配、质量证据和整箭质量对账；
- 在严格指纹和窄适用域内启用的 RealChute settled mass 生产证据链；
- 较完整的单元、集成、API 与静态前端回归。

但项目目前仍不应标记为“发布完成”。它已经达到**桌面端、单一已校准火箭的可用研究工具**水平，尚未达到**可长期维护、可批量导入、可审计恢复、跨设备稳定使用**的发布水平。

发布阻断项不是继续增加更多公式，而是：

1. 修复任务结果页的移动端横向溢出；
2. 建立 SQL/YAML 一致性检查与显式恢复流程；
3. 补齐数据来源、人工确认、置信度和旧数据迁移状态；
4. 建立 Git/README/依赖锁定/备份恢复等工程基线；
5. 用真实 KSP 样本完成 VAB 导入端到端验收；
6. 在详细任务验证中明确处理或拒绝有限推力、并联燃烧、级寿命等尚未建模的物理语义。

因此，后续必须按照本文第 7 节的 M0 → M4 顺序执行。旧的 `AI_STAGED_IMPLEMENTATION_PLAN.md` 只保留为历史计划，不再作为当前进度和执行顺序的权威来源。

## 3. 当前系统真实架构

```text
dashboard/
  index.html + css/dashboard.css + ES modules
       │
       │ HTTP / JSON
       ▼
server/
  routes_*                  Flask API
  models.py                 SQLite + YAML 双写
  database.py               迁移、首启导入、索引
  import_service.py         VAB/批量预览与确认
  vab_parser.py             craft 结构与发动机组证据
  ksp_*                     安装索引、匹配、质量证据、取证与对账
  mission_analysis.py       统一任务分析服务
       │
       ├── compute_c3_mass.py
       ├── mission_adapters.py
       ├── mission_solver.py
       ├── mission_parking_replay.py
       ├── mission_stage_planner.py
       ├── mission_payload_evaluator.py
       └── mission_capacity_search.py
       │
       ▼
c3_plot.db + rockets/*.yaml + output/*/data.json
```

权威性必须区分：

- SQLite 是当前运行时主数据；
- YAML 是写穿备份和恢复输入，不是已经证明永远同步的第二主库；
- `output/*/data.json` 是可再生成的计算产物；
- `.craft` / `.loadmeta` 是来源证据和草稿输入，不是可直接信任的级段性能真值；
- KSP ConfigCache、DLL 指纹和受控实验只在其明确适用域内提供证据。

## 5. 对旧结论的纠正

### 5.1 RealChute 不再是“仅实验、未接生产”

当前生产链已经是：

```text
import_service.preview_craft
  → ksp_runtime_provenance
  → extract_part_mass_evidence
  → realchute_part_settlement_evidence
  → reconcile_craft_mass
```

`REALCHUTE_PRODUCTION_AUTHORIZATION` 已存在，并对 ConfigCache、RealChute DLL、部件、材料、模式、降落伞数量和直径范围做严格门控。旧复盘中“尚未接入生产”的结论已经过时。

这不代表 RealChute 已被普遍支持。当前正确表述是：**受控实验支持的窄域 settled mass 已接入；任何指纹不符、Automatic 模式、其他材料/部件/多伞或区间外直径仍必须失败封闭。**

### 5.2 旧八阶段计划的进度描述已经失真

`AI_STAGED_IMPLEMENTATION_PLAN.md` 仍写着“当前只执行阶段 1”，但阶段 2～5 的任务数据模型、求解器、后端接入和前端展示已经存在；阶段 6 的大量 KSP 证据工作也已完成。继续逐字执行旧 Prompt 会造成重复实现或破坏现有边界。

`PROJECT_BASELINE_AUDIT.md` 指出的 SQL/YAML 一致性工具缺失、数据来源不足、README/发布验收未完成，目前仍然成立，应合并到本文 M0/M1，而不是继续保留为分散待办。

## 6. 风险与问题清单

### P0：发布前必须解决

#### P0-1 移动端任务结果横向溢出

- 复现：390 × 844 视口，打开 GEO 查询并展开详细验证；
- 现象：页面文档宽度大于视口；`.capacity-table` 固定 `min-width:720px`，详细行和 `.timeline-table` 继续撑宽父级；
- 影响：用户必须横向拖动整个页面，侧栏、表单和结果区不能稳定使用；
- 修复方向：让 `.orbit-results` / `.capacity-section` / 表格容器成为受约束滚动区域，给 grid/flex 子项补 `min-width:0`，禁止表格最小宽度传播到文档根；
- 验收：390、768、1280 px 下 `documentElement.scrollWidth <= clientWidth + 1`，表格自身允许局部横向滚动，侧栏和按钮仍可操作。

#### P0-2 无可审计的版本与恢复基线

- 当前无 Git 工作树、README、`.gitignore` 和依赖锁；
- 在任何大改之前，必须先确定源码、数据库、YAML、VAB 证据、实验证据和生成物的纳入/忽略策略；
- 不得为了“干净仓库”删除 `c3_plot.db`、VAB 文件或实验输入；
- Git 初始化、提交或推送必须单独执行并保留当前文件时间与证据哈希，不得伪造历史。

#### P0-3 SQL/YAML 漂移不可观测

- 当前 CRUD 有双写和回滚，但没有全库只读一致性报告；
- 必须先实现检测，再实现人工选择方向的修复；
- 禁止启动时静默覆盖任何一侧。

### P1：稳定日常使用前必须解决

#### P1-1 数据来源与人工确认状态不完整

- 当前 `import_sources=0`，已有 Neutron 数据无法证明来自哪份 VAB/人工校准；
- 旧数据只能标记为 `legacy_unknown` 或“人工录入、来源未回填”，不能伪造导入时间、KSP 版本或模组指纹；
- 火箭详情和任务结果需要显示简洁的数据质量摘要。

#### P1-2 发动机选择存在同名歧义

以下名称各对应两个 CFG，编辑器当前只显示名称：

- `24-77 "Twitch" Liquid Fuel Engine`；
- `LFB KR-1x2 "Twin-Boar" Liquid Fuel Engine`；
- `LV-T30 "Reliant" Liquid Fuel Engine`；
- `LV-T45 "Swivel" Liquid Fuel Engine`。

下拉框应显示可区分的 CFG/版本标识，并保持保存值为唯一 `cfg_filename`。

#### P1-3 VAB 批量导入缺少发布级端到端证据

自动化测试覆盖了合同和失败路径，但当前数据库没有真实导入来源记录。本阶段必须在数据库副本上使用代表性 VAB 样本完成预览、人工修正、确认、重复导入、回滚和 SQL/YAML 对账。

### P2：模型可信度提升

#### P2-1 详细验证仍不是完整任务仿真

当前明确未模拟：

- 有限推力和燃烧时间；
- TWR 与重力损失随燃烧过程变化；
- 级寿命、滑行时间、推进剂沉底/点火条件；
- 并联级同时燃烧与助推器提前分离；
- 一次燃烧跨级接力。

这些限制不妨碍当前模型用于校准域内筛选，但必须继续显示为 `estimated`，不能升级为 `exact`。

#### P2-2 动态质量模块的泛化证据不足

RealChute 仅完成一个严格窄域。其他部件、材料、Automatic、多伞，以及 RealFuels/ModuleFuelTanks 等动态语义都必须遵循“无受控证据，不启用生产估算”。

### M1：数据一致性、来源与恢复

#### 目标

让每一枚火箭都能回答“数据从哪里来、是否人工确认、SQL/YAML 是否一致、如何恢复”。

#### 工作包

1. 实现只读一致性命令/API，输出：`sql_only`、`yaml_only`、`different`、`matching`、`invalid`；
2. 定义规范化比较，排除仅格式/键顺序差异，但不忽略数值或发动机组差异；
3. 实现显式修复：SQL → YAML 或 YAML → SQL，执行前备份并展示差异；
4. 补齐来源模型：源文件、SHA-256、导入时间、KSP/模组指纹、解析器警告、人工确认状态和质量等级；
5. 对现有 Neutron 数据标记真实的未知边界，不补造历史；
6. 在火箭详情与任务结果中显示来源/置信度摘要；
7. 建立数据库 + YAML 的备份和恢复演练。

#### 验收门

- 四种漂移场景均有自动化测试；
- 修复方向必须由调用方明确指定；
- 任一侧写入失败时不留下半更新状态；
- 备份副本能够恢复出相同业务数据和计算结果；
- 旧数据明确显示 `legacy_unknown`，而不是伪造“已验证来源”。

### M2：VAB/KSP 导入发布化

#### 目标

把现有强大的取证链变成用户可重复完成的安全导入流程，而不是把草稿自动包装成性能真值。

#### 工作包

1. 建立真实样本矩阵：普通单发动机、SSTU Triple/SixRadial、混合发动机组、并联助推器、MultiModeEngine、未知部件、RealChute 授权内/外；
2. 在预览 UI 展示结构化警告、匹配候选、布局证据、质量残差和需要人工确认的字段；
3. 质量、级段、发动机映射和至少 3 个校准点未确认时禁止确认导入；
4. 目录批量导入实现可审计逐文件结果、重复检测、更新/跳过选择和失败隔离；
5. 导入后立即运行 SQL/YAML 一致性检查和计算回归；
6. RealChute 严格保持授权门；任何扩域必须新增受控实验和指纹证据。

#### 验收门

- 代表性样本全部有预期的成功或失败封闭结果；
- SSTU 台数来自保存布局和安装索引，不能由 `PART` 数量代替；
- 混合发动机在 `engine_groups` 中不丢失；
- `.craft.original` 不被当成独立新火箭；
- 未确认质量和校准不能进入生产计算；
- 重复导入不产生重复火箭或孤立记录。

### M3：任务模型可信度升级

#### 目标

保持当前校准模型可用，同时逐项替换“已知但未模拟”的关键物理简化。

#### 执行顺序

1. 先建立模型版本和能力标志：当前模型命名、假设、支持/不支持语义；
2. 为有限推力、燃烧时间、TWR 和级寿命定义纯数据合同；
