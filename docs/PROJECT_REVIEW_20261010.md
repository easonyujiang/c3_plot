## 1. 总体判断

值得继续维护，适合先修正模型和数据边界，再逐步扩大使用范围。当前属于功能完整度较高的个人研究工具：火箭资料管理、曲线展示和理想任务序列都有可用实现；但任务推荐的可信边界存在实质缺陷，不能把页面上的“详细验证通过”当作实测支持或完整飞行可行性证明。

不建议整体重写。纯计算层、任务状态合同、数据库访问层、导入预览与 KSP 质量证据链都有保留价值。当前主要问题是各层对同一物理量、校准范围与数据版本的解释不一致，而不是缺少更多功能。

目录有 2026-10-10 的修复记录，说明当前状态已经不同于 7 月与 8 月的旧审查。本报告以此次读取和复现为准，没有照抄旧待办。此前移动端文档级溢出、README 缺失等问题不能再直接列为当前缺陷。

## 3. 做得好的地方

### 3.1 任务层的组织有实际价值

任务计算已拆分为输入适配、级段状态、燃烧求解、停车轨道回放、任务规划、载荷评估和容量搜索。使用明确的结果类型、失败原因、推进剂与质量记录，便于定位失败发生在哪一步。容量搜索保留可行下界、不可行上界、容差和评估次数，比只输出一个数值更可审查。

### 3.2 不确定的导入数据没有被普遍当成真值

VAB 输入经过结构解析和证据检查；并联级在详细串联回放中被拒绝。RealChute 的生产支持受实验结果、ConfigCache/DLL 指纹、部件、材料、手动模式和直径范围约束，越界保持 unresolved。这类“证据不足时停止下结论”的设计应保留。

### 3.3 工程基线已经有明显改善

当前具备 README、运行依赖快照、数据对账、备份恢复、YAML 原子替换和异常回滚，以及不少边界测试。界面有完整业务流程，移动端表格能局部滚动。907 项测试的存在和通过说明维护资产相当丰富，但不代表下面这些跨层错误已经被覆盖。

## 4. 已复现问题：按修复优先级排列

P1 表示可能改变运力、可行性或推荐结论；P2 表示数据追溯、查询行为或维护流程缺陷。这些级别针对本地研究工具，不等同于已经发生现实飞行损失。

### P1-1 发射方向修正没有进入详细任务验证

位置：compute_c3_mass.py:411–449；mission_payload_evaluator.py:435–491；server/routes_data.py:241–257。

compute_orbit_mission 把 dv_launch_plane 加入 required_dv，但没有把它纳入后续 burn_sequence；详细评估从该序列读取任务燃烧，从固定曲线重建上升段，没有补入这一修正。详细结果又是最终推荐依据。

独立复现：同一火箭，目标 35786 km，停泊 220 km，指定载荷 0.4 t：

| 目标倾角 | 页面总需求 | 发射方向修正 | 快速估算运力 | 详细运力 | 详细状态 |
| --- | ---: | ---: | ---: | ---: | --- |
| 0° | 4112.1 m/s | 0.0 m/s | 0.502 t | 0.502225 t | verified_feasible |
| 180° | 4986.3 m/s | 874.2 m/s | 0.134 t | 0.502225 t | verified_feasible |

两者的详细上升需求和任务时间线完全相同。逆行任务快速估算已判定 0.4 t 不可行，详细验证却推荐可行。这里不是快速估算一定比详细模型准确，而是详细模型漏用了项目自身明确定义的需求项。

修复方向：让参考发射条件差异真正改变停车轨道回放的质量/推进剂状态，并明确修正属于上升过程；不要随意把它当成一次上面级点火。增加参数变化的跨层守恒检查。

### P1-2 模型生成范围被标为实测校准范围

位置：compute_c3_mass.py:208、299；mission_payload_evaluator.py:186–198；mission_capacity_search.py:122–164。

真实校准点载荷是 1.055、2.5、4.0 t。compute_rocket 拟合二次损失后，在约 0.05–4.9961 t 生成 dv_curve；calibration_payload_bounds 直接用生成曲线的端点作为“校准范围”。因此搜索器所说的“校准范围内、无外推”实际只保证不超出已生成曲线。

当前 GEO 详细运力 0.502225 t，低于最低实测校准载荷 1.055 t；0.4 t 请求也得到 verified_feasible，警告没有明确说明它处于实测范围外。

修复方向：单独保存实测支持域、模型生成域、校准条件与拟合版本。实测范围外可保留研究估算，但应标明外推并采用不同置信度/推荐规则。需要在约 0.5 t 附近补真实校准或独立验证，才有依据增强该数值的可信度。

### P1-3 改变停泊高度后，仍把原曲线视为已覆盖校准

位置：compute_c3_mass.py:339–500；mission_payload_evaluator.py:477；server/mission_analysis.py:430–466。

查询允许修改 parking_alt_km，轨道转移需求随之改变；但详细回放仍由原 220 km dv_curve 计算上升段状态。返回值 covered_by_calibration 无条件为 True。

复现：载荷 0.4 t，将停泊高度从 220 改为 400 km：

- 两次 calibrated_remaining_dv 都是 4329.32097 m/s；
- 两次 ascent_required_dv 都是 8984.37588 m/s；
- 转移总需求由 4112.1 改为 4046.2 m/s，详细容量由 0.502225 改为 0.534829 t；
- 400 km 仍被标为 covered_by_calibration=True。

这不能证明 400 km 的实际运力一定降低或增加多少；它证明模型没有处理改变初始条件所需的校准转换。修复前应限制到已有参考条件，或返回条件不匹配/估算状态。

### P1-4 并联虚拟阶段重复计入芯级剩余质量

位置：compute_c3_mass.py:39–48、126–185。

并联展开的 phase1_wet/dry 已包含芯级；phase2 又保存芯级剩余质量。随后按串联堆栈运行 total_vac_dv 时，phase2 的湿质量被当成“上方质量”再次加到 phase1 上。

用同为 300 s 比冲的简单可解析例子复现：助推湿/干 10/2 t，芯级湿/干 20/4 t，推力比 80/100，载荷 1 t。助推耗尽时芯级剩余 10 t。

独立质量记账应为：

Δv = 300 × g0 × [ln(31/13) + ln(11/5)] = 4876.3426 m/s。

项目虚拟阶段为 (30,12) 与 (10,4)，串联公式给出 4020.3398 m/s，差 -856.0029 m/s。这是记账错误，不是未建模大气或有限推力导致的偏差。

当前基线火箭没有并联级，详细验证也会拒绝并联，因此此项不直接解释基线 GEO 数值；但会影响接受 parallel 配置的传统 C3/Δv 计算。校准拟合还可能在校准点附近掩盖该结构错误。

修复方向：按物理状态计算同时燃烧和分离阶段，避免把含芯级的组合状态当成独立串联级；加入质量守恒和等比冲解析例子的独立验证。还应检查芯级先耗尽时的事件顺序。

### P1-5 超出 C3 上限时，末端载荷被当成有效能力

位置：server/models.py:568–579；server/routes_data.py:129–151。

interpolate_payload 对超过最高 C3 的请求返回最后一个曲线点的 payload。当前末点约为 C3=51.74、载荷 0.0069 t。

复现：POST /api/find，C3=1000、载荷 0.00345 t，返回 capacity=0.007 t、feasible=True。问题也出现在实际界面：Jupiter 参考任务 C3=55 超过现有曲线范围，本来 compute_rocket 计算结果为空，GET /api/data 的补值逻辑又把末点约 7 kg 填回，详情页显示它有运力。

修复方向：区分域内插值、域外无能力与无法估算；超出高 C3 边界不能延续末端正载荷。补值逻辑必须遵守同一个定义，已有任务结果为空也不能直接推断为需要补一个正值。

### P2-1 发动机重载静默跳过正在使用的发动机

位置：server/database.py:316–340；server/models.py:509–514；migrations/001_initial_schema.sql:45–49。

_import_engines 使用 INSERT OR REPLACE，替换会涉及删除旧行；stage_engines 对 engine_id 设置 ON DELETE RESTRICT。对当前火箭使用的两种发动机发生外键失败，异常被逐文件捕获打印，接口最后仍返回 200 和 74 个发动机。

临时数据库复现日志：

- WARN engine SC-ENG-LR81-8096.cfg: FOREIGN KEY constraint failed
- WARN engine SC-ENG-Merlin-1B.cfg: FOREIGN KEY constraint failed

没有引用的发动机重新获得 ID，被引用的发动机没重载成功。详细任务适配层又直接读取磁盘 CFG，而持久化运力曲线没有依赖指纹或失效判断，修改 CFG 后会存在新发动机性能与旧曲线混用的风险；后者为源码推导，本次未改写正式 CFG 做复现。

修复方向：保留发动机 ID 的 UPSERT；明确报告失败文件；用发动机/配置/模型指纹判断曲线是否需要重算。

### P2-2 普通导入路径仍不保存来源

位置：server/routes_import.py:58–64、83–124、174–197；server/models.py:278、302、380。

批量管线可传 source，但 YAML 上传、粘贴和 VAB 确认路径调用 create/update 时不传来源。临时副本中新建一个粘贴导入火箭，接口返回 201，但 import_sources 对应记录为 0。

因此“来源未回填”不仅是旧数据问题，新导入也会继续产生无来源状态。VAB 预览携带的信息也需要与最终人工修改和确认记录形成关系。

修复方向：统一导入保存入口；记录原文哈希、格式、解析版本和已知来源。人工确认应单独记录，不把一次保存或点击等同于已核验全部质量与校准。

### P2-3 C3=0 的高级筛选条件被跳过

位置：server/models.py:765。

条件使用 if filters.get('min_payload_at_c3') and filters.get('c3_target')，把合法的 C3=0 当成没有提供参数。

复现：POST /api/query，min_payload_at_c3=999999、c3_target=0，仍返回现有火箭 count=1；正确行为应当筛除它。

修复方向：判断参数是否存在/是否为 None，并校验类型和有限性。查询 API 也应与 mission-query 共享一致的输入错误合同。

## 5. 维护与研究可信度评价

| 维度 | 判断 | 依据 |
| --- | --- | --- |
| 功能完整度 | 较好 | 管理、曲线、规划、导入和证据链已有实现 |
| 本地基础稳定性 | 较好 | 907 项测试及只读数据库审计通过 |
| 任务结果可信度 | 需要优先修正 | 漏算需求项、校准域混淆、初始条件不匹配已复现 |
| 数据追溯 | 部分具备 | 证据系统较细，但普通导入和现有火箭来源不足 |
| 维护便利性 | 中等 | 模块职责清楚，仍有大文件、重复参数和旧入口/旧文档 |
| 推广成熟度 | 暂不充分 | 单一基线火箭、多环境与真实批量验证不足，未建立 Git 历史 |

当前目录不是 Git 工作树，不能审查提交历史或证明某个已知版本可回退。README 和依赖快照虽已补齐，仍应建立可识别的版本基线。迁移按文件在每次启动执行，缺少明确已应用版本登记，长期升级需要更清楚的迁移状态与失败恢复设计。

KSP 实验/IL 取证已经成为很大的子系统：ksp_mass_control_experiment.py 超过两千非空行，多个 KSP 模块超过千行。它们有证据价值，不应为了目录干净而删除，但应与日常运力查询形成更清楚的组件边界，避免每次维护都需要理解全部模组实现。

存在 main/state/overview 的旧版与 v2 文件，当前活跃入口为 main-v2.js，旧文件不是本次发现的运行阻断。保留历史文件可以，但需要标明活跃入口、减少多版本加载标识的混用。物理常数在计算模块与 server/config.py 中重复，也增加以后修改参考条件时发生分歧的机会。

文档材料充分，权威性却仍容易混淆：FINAL_ROADMAP 前文保留旧目录和已修复待办，末尾追加新的验收补充；ORBIT_CAPACITY_MODEL 把逆行详细结果约 0.502 t 写成模型能力，而本次发现它与漏用发射修正有关。建议将“当前有效状态”集中维护，历史验收继续保留并标注被哪些新发现修正。

测试主要证明内部合同、自检和回归稳定；真正缺少的是能打破共同错误假设的独立检查。例如：生成范围不能自动等于实测范围；改变发射方向必须改变燃料状态；改变停车轨道不能仍声称原条件覆盖；串并联展开必须满足质量守恒；超出能力边界不能继续可行。它们比继续累计相似断言更有价值。

界面已有完整设计，当前修复重心不应是换视觉样式。三种视口下核心查询可用，但移动端整页较长，信息表格需要局部横向滚动；这是体验取舍，可以后续整理。首先应使结果中“估算”“模型内验证”“实测支持”具有清楚且一致的含义。

## 6. 建议的推进顺序

1. 先修复 P1-1 至 P1-5，建立跨层需求守恒、独立质量记账和实测支持域判断。修复前将超域/条件不匹配结果降级为明确估算或数据不足。
2. 统一发动机更新、曲线版本、导入来源和查询校验。继续保持 SQL/YAML 只读对账与明确修复方向，不静默覆盖数据。
3. 为当前源码建立版本控制和简洁验收入口，保留数据库、VAB 和实验材料的独立备份；完善迁移版本登记。此次审查不执行这些治理变更。
4. 增加约 0.5 t 的真实校准/独立验证，以及至少一组不同火箭和并联模型的对照样本，检验泛化能力。
5. 在上述结果稳定后再决定有限推力、燃烧时长、重启次数、级寿命和更广模组支持。它们是扩展功能，不应代替修复当前模型已有输入的解释错误。

继续维护的价值明确：现有业务闭环和证据系统已经省去了大量从零建设工作。需要优先恢复的是结果的可解释性和可信范围，而不是扩大功能清单。
