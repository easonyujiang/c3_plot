# 火箭运力、型号覆盖与发射程序路线图（2026-10-21 历史版）

> **历史文档，已归档。** 当前产品方向以 [产品路线图：运力百科与自动校准](../PRODUCT_ROADMAP.md) 为准。本文保留用于追溯旧阶段划分。

更新：2026-10-24（补充当前进展，已归档）。本文根据使用者的实际目标和本机游戏安装核查制定，是当时的产品方向与执行顺序入口；历史路线保留用于追溯。

## 产品目标

把自己设计的火箭变成一套能回答以下问题的工具：

1. 这枚火箭向指定轨道最多能送多少净载荷？
2. 给定载荷和任务，现有型号中该选哪枚，哪些任务仍缺型号？
3. 该从哪里、何时、以什么飞行程序发射，如何用 MechJeb 执行并验证？

建议定位为“面向个人 KSP/RSS 火箭库的运力测定、覆盖分析与发射规划工具”。核心界面按任务选择与型号比较组织；C3 曲线作为性能分析视图。

## 本机条件与设计决策

本轮只读核查的游戏是 KSP 1.12.5.3190。当前 MechJeb DLL 文件版本 2.14.2.0，kOS 1.6.0.1；安装中包含 RSS、FAR、RealFuels、SMURFF、SSTU、Principia 等，详见 [安装分析](../ksp/KSP_INSTALLATION_AUDIT_20261021.md)。

- 第一执行器选 MechJeb 2.14.2 的 PVG。先复现当前用户的发射方式，再围绕它搜索参数。
- 保留现有经验模型作为快速估算器，加入游戏实飞结果和可重复试验。模型负责筛选候选，游戏负责验证边界。
- 先完成地球圆轨道和椭圆轨道的运力库，再扩展具有具体方向与时间约束的逃逸、月球和行星际任务。
- 接口优先使用版本对应的源码；源码和 DLL 不一致时再做有针对性的只读 IL/反编译核查。
- 2026-10-21 已分析源码和安装文件；2026-10-24 已完成一个隔离控制/检查插件和一次真实飞行。尚未做批量发射、载荷边界搜索或最优解证明。

## 当前进展（2026-10-24）

- 已建立隔离基线 harness：`prepare_baseline` 生成一次性存档，插件核对存档/craft/Mod/DLL 哈希并在明确门槛后飞行，`audit_baseline` 只读判定，`freeze_baseline_evidence` 固化证据。
- `C3Baseline20261024F` 已完成 **1.000 t → 220 × 220 km、20°** 的 `target_verified` 飞行，保持 30.62 s，载荷完整，整流罩已抛弃。见 [证据包](../evidence/C3Baseline20261024F/README.md)。
- `C3Baseline20261024G` 已完成 **2.500 t → 220 × 220 km、20°** 的 `target_verified` 飞行，保持 30.60 s；载荷为现有 payload 舱内质量模拟件。见 [证据包](../evidence/C3Baseline20261024G/README.md)。
- 这完成了阶段 0 的最小闭环和阶段 1 的**前两个载荷点**；它不证明最大运力，也不是重复性统计。
- 下一步：补第三个载荷点（例如 4.0 t，失败则回退 3.0 t），把 1.0/2.5/第三个点转成可复核的 C3 校准；随后进入阶段 2 的型号覆盖矩阵。

## 运力的定义

每个运力结果必须绑定：火箭设计版本、载荷形状/安装方式、目标轨道、发射场、发射时间或时间窗口、环境指纹、飞行程序和完成条件。

净载荷指最终交付的有效载荷，适配器、载荷舱和随载荷交付的辅助设备要显式分类，整流罩按实际抛弃事件记账，不能全部作为一个静态扣减。载荷不能只改质量而忽略 FAR 下的尺寸、外形和位置变化。

圆轨道至少描述高度和倾角；椭圆轨道描述近地点、远地点和倾角。需要指定轨道平面、定点或交会时，再加入 LAN、历元、目标相位及参考系。SSO 还需验证实际环境中的轨道面进动，不能仅凭一个倾角将任务判为太阳同步。

任务完成条件包括轨道允许误差、检查时点/保持时间、剩余推进剂或 Δv、点火次数、电量、温度和飞行完整性。GTO 与 GEO 交付分开记录，月球转移与月球捕获分开记录。相同 C3 并不保证具有相同出发方向、窗口和可执行性。

界面并列展示：估算运力、实飞验证成功载荷、已测试失败/不可行边界，以及带余量的建议载荷。没有试验的数据明确显示待验证；不能把曲线插值显示为实测。

## 阶段 0：固定可重复的游戏和发射基线

交付：安装指纹、火箭版本、任务定义、MechJeb 配置快照与试验记录格式。

- 以 ModuleManager 最终缓存、实际 DLL 哈希、编辑器/发射台快照为依据，记录每个发动机的最终配置、燃料、推力、节流与点火限制。
- 导出当前天体与发射场参数，替换目前固定的地球/220 km/发射纬度假设；记录难度设置、物理时间步和影响试验的模组选项。
- 区分 CKAN 登记版本、DLL 文件版本、实际加载状态；记录 Principia 是否在目标存档成功初始化以及所用参考系。
- 对当前 MechJeb 保存配置做只读快照并人工核对；全局保存值不是每枚火箭的实际使用值。
- 用独立存档副本和试验载荷运行，记录原始输入哈希及恢复检查。游戏安装和正式存档的变更另行按试验方案执行。

验收：同一构型、任务、发射配置和初始条件能重复执行；每条结果能追溯至实际文件和设置。先处理 `.dll.new` 所代表的版本选择，不能在一组试验中悄然升级 MechJeb。

## 阶段 1：获得第一枚火箭的轨道运力表

交付：一个代表型号在若干目标轨道下的运力、建议载荷和可复现发射参数。

建议先用 Neutron I 2630 作为端到端样本，人工确认构型和历史校准点后建立新的试验基线。首批任务模板可包含 220 km/400 km 圆轨道、一个较高倾角任务、220 × 35786 km 转移轨道；倾角由实际发射场和任务决定。这些是待测模板，不是已验证能力。

1. 从保守载荷起步，固定 MechJeb 程序完成一次完整发射并记录任务成败。
2. 在同一程序下逐步增加载荷，定位成功与失败边界。
3. 在局部单调性成立时采用二分缩小载荷边界；遇到分级策略、制导收敛和构型变化时分支探索，不能把一次失败直接当作物理上限。
4. 对边界附近与建议载荷重复试飞，区分燃料不足、制导失败、点火失败、结构失效和目标轨道误差。
5. 留出未参与拟合的轨道/载荷作独立验证，以实际误差决定插值适用范围。

初始可把载荷搜索容差设为 `max(10 kg, 1% 当前载荷)`，轨道误差和建议余量按任务配置；这些是试验配置起点，需经飞行调整。少量重复只能说明重复性，不足以宣称统计成功率。

验收：用户输入一个已覆盖的目标轨道，能看到估计值、最高验证成功载荷、建议值、适用程序和验证记录；保持与现有曲线模型的差异可解释。

## 阶段 2：建立火箭库覆盖图与型号缺口

交付：任务 × 火箭的运力矩阵，按轨道/倾角筛选的比较图，以及新型号建议清单。

- 从常用存档的 VAB craft 批量建立候选列表，用内容指纹去重，区分火箭主体、载荷配置和同型号修订。当前多个存档的 craft 数量不能直接当成型号数。
- 每个矩阵单元记录估算、验证、未知、构型不支持或任务不可行；每条边界都注明使用的发射程序。
- 对任务需求集合统计未被覆盖的载荷与轨道组合，并按需求频次或用户优先级排序。
- 成本来源可靠时，比较单次发射成本、单位载荷成本及余量；成本未知时，只能显示载荷利用率或型号过剩程度，不能宣称经济最优。

必须区分两类缺口：

| 类型 | 判断 | 输出 |
| --- | --- | --- |
| 能力缺口 | 某目标任务没有可用型号，或所需载荷超过已支持/验证范围 | 需要多大运力、什么轨道/点火能力的新型号 |
| 经济性或使用体验缺口 | 现有型号能完成任务，但利用率低、成本高或流程复杂 | 建议补充较小型号或上面级的目标任务范围 |

同一任务下，能送 5 t 的火箭通常也能送 2 t；缺少“额定 2 t 型号”不自动构成 2 t 的能力缺口。FAR 稳定性、制导下限等特殊限制需要实测，不能一律假设所有轻载都可行。

第一版由用户定义需求分箱，例如若干载荷档 × LEO/GTO/GEO/极轨任务；没有需求记录时展示覆盖情况，不推断用户应该设计哪枚火箭。实现后再用实际任务记录形成优先级建议。

验收：针对一组已定义需求，能够解释“哪枚可用、证据是否充分、缺哪个任务能力、为何建议新增某型号”。

## 阶段 3：自动试验与 MechJeb 发射参数优化

交付：可排队执行的试验任务、飞行参数档案、失败分类、最佳已验证方案与对比记录。

先实现一个小型 `MechJeb 2.14.2 adapter`，优先复用已有 C3 游戏插件。按版本对应的 API 读取当前主 MechJeb core、设置目标与参数、申请/释放 autopilot 的用户控制权，并读回确认。源码中的 `ascentPathIdxPublic` 会完成路径模块切换；直接改私有配置字段或只写文件不能保证运行时切换生效。

外部 Python 负责试验调度、参数搜索和结果归档；游戏内 MechJeb 负责低层制导、姿态、节流与分级。使用带任务 ID 的本地命令/结果协议，设置前置检查、命令确认、超时、取消和恢复。试验失败或游戏崩溃保留日志，恢复到已知的发射前状态。

```mermaid
flowchart LR
    A[目标轨道与载荷] --> B[Python 试验调度与参数搜索]
    B --> C[C3 游戏内适配器]
    C --> D[MechJeb PVG]
    D --> E[实际游戏物理与模组]
    E --> F[遥测、事件与任务判定]
    F --> B
    F --> G[运力库与型号覆盖图]
```

优化分两步：固定载荷改善轨道误差、余量和飞行约束；再以最佳候选参数搜索更高载荷。首先搜索俯仰开始速度、俯仰速率、PVG 接入条件、滑行段和分级/整流罩事件，遵守发动机真实节流、再点火、沉底和供电约束。搜索区间先通过保守试飞建立，不把全局保存值当作通用推荐参数。

输出两种运力：固定标准程序下的可比较运力，以及各型号/任务分别优化后的最佳已验证运力。这样既能比较火箭本身，也能识别飞行程序带来的提升。

验收：一个任务可以完成“配置 → 发射 → 遥测 → 判定 → 调参 → 复飞”，失败可追溯；最终方案比基线的提升可在留出的试飞中重现。

## 阶段 4：提供可执行的发射方案和程序

交付：针对具体火箭/任务的发射方案包，而不是一组脱离环境的参数。

方案包包含 craft 与环境指纹、载荷、场址、UT/窗口、目标轨道/参考系、MechJeb 版本及参数、事件时间线、约束、预期终态、验证记录和失败处置。时间线覆盖点火、解锁支架、重力转弯、限 Q/加速度、分级、沉底、再点火、抛罩、关机、入轨及后续机动。

先交付 MechJeb 参数档与人工确认执行，再交付游戏适配器执行的任务配置。kOS 用于可选的事件编排、检查与日志，或独立的脚本制导实验；若需要由 kOS 调用 MechJeb，则先验证额外桥接组件或实现自己的适配层。

目前已经存在第三方 [kOS.MechJeb2.Addon](https://github.com/belpyro/kOS.MechJeb2.Addon)，其文档描述了 `ADDONS:MJ` 访问及上升包装；这不等于已安装、支持当前 PVG 版本或覆盖所有所需参数。历史 [kRPC.MechJeb](https://github.com/genhis/KRPC.MechJeb) 也只能作为候选，必须先做版本、PVG、主 core 绑定和启停行为的兼容测试。标准 kOS 或标准 kRPC 的存在均不能直接证明 MechJeb API 可用。

任何时候只能有一个执行器控制姿态、油门和分级。MechJeb 飞行时，kOS 观察或编排，不同时锁定油门/转向。增加 kOS 部件、适配器或资源会改变质量及电量需求，需进入构型指纹并重新验证。

验收：选择任务和火箭后能生成可重放方案；执行端检查指纹、能力、单位和前置条件；接口不匹配时给出明确原因。

## 阶段 5：有限推力与 Principia 任务扩展

交付：低推重比上面级、长时间滑行、真实出发方向和窗口受约束的任务方案。

先用现有燃烧序列求解器做快速可行性筛选，逐步加入有限燃烧时间、级寿命、蒸发、沉底/再点火和电量预算。FAR 上升段优先以游戏试验校正；离线快速模型需单独验证，避免为第一版运力表重写整套游戏物理。

Principia 路线应读取目标存档中实际运行的参考系和轨迹数据，区分瞬时密切轨道参数与长时间多体传播。地球逃逸 C3 作为参考时需说明历元与计算定义；月球到达、捕获、逃逸方向和远期任务成功由实际轨迹/积分验证。

验收：每种新增任务都有可复现的实飞案例或独立参考；未验证的多体任务不会仅因二体 Δv 余额为正就判定可执行。

## “最优”的产品表达

默认目标是在满足轨道误差、飞行约束和余量的前提下最大化净载荷。对于指定载荷，也可选择降低发射成本、减少燃料消耗或缩短任务时间；这些目标可能冲突，需要显示取舍。

结果称为“在给定构型、环境、约束与搜索范围内的最佳已验证方案”。保存搜索范围、试验次数和未探索区域，暂不承诺全局最优。MechJeb 的轨迹优化也不能直接视为整枚火箭、所有载荷及所有任务的全局最优证明。

## 下一轮应直接做的工作

选择一个常用存档和一枚代表火箭，完成阶段 0 与阶段 1 的最小闭环：读取并核对当前 PVG 参数 → 固定任务和载荷定义 → 扩展遥测 → 一次完整基线发射 → 一组载荷边界试验 → 展示该型号的轨道运力表。随后建立阶段 2 的矩阵，再扩展自动优化。

CI、备份恢复和版本治理随这些阶段实施，优先保护构型与试飞证据。完成本文件不表示这些功能已经落地，也不表示当前火箭库的运力缺口已被测定。
